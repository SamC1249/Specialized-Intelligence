# Adversarial-Agent Plan — 2026-11-11

> No fresh Adversarial-Agent authored a plan for today, so `Coding-Agent`
> is carrying forward the unresolved risks listed at the bottom of
> `docs/plan-2026-06-20.md` (multilingual gap, license-classification
> fragility, no cross-source dedupe, no yield estimate). Each item below
> is written to be falsifiable against the existing fixture set so the
> next reviewer can audit whether we actually moved the needle.

## Hypotheses under test

> **H2.** A metadata-only *cooking-domain relevance* signal, computed
> from a hand-curated multilingual cooking lexicon, materially re-ranks
> the baseline backlog *without hurting* license-clean recall — i.e. a
> `v2` quality profile Pareto-dominates the `baseline` profile from
> `reports/baseline-2026-06-20.json` on the exact same fixtures.

> **H3.** Across our four license-clean sources (`wikimedia`,
> `archive_org`, `peertube`, `common_crawl`) the *cross-source duplicate
> rate* on identical procedural footage is non-trivial (>5%) once we
> normalize title + duration-bucket, meaning any production yield
> estimate that sums raw per-source counts is systematically inflated.

> **H4.** A per-source *yield estimator* that only uses listing-API
> metadata (declared `totalHits`, hits per 1k crawled pages, etc.) is
> good enough to rank sources by order-of-magnitude yield, which is all
> we need to decide which source to invest the next crawl-day in.

## Adversarial questions

1. **Does the lexicon overfit English?** Add fixtures in at least one
   non-English language (ES/FR/DE/IT/JA) and prove the `v2` profile
   does **not** drop multilingual records to zero.
2. **Does dedupe destroy license-clean records?** When two sources
   report the same recipe and one is CC-BY and the other is `UNKNOWN`,
   dedupe must prefer the license-clean record, never the opposite.
3. **Is our yield estimate honest?** The yield CLI must distinguish
   "N listed on upstream" from "N parsed into redistributable
   `VideoRecord`s" and emit both numbers.
4. **Are new profiles comparable?** Any new scorer must be registered
   in a `PROFILES` table and runnable via `python -m specint compare
   --profile <name>`; the resulting JSON lands under `reports/` so the
   next PR can diff.

## Risks the next reviewer should challenge

- The lexicon is still hand-curated and English-centric in weight; the
  i18n fixtures prove non-zero recall, not actual ranking quality.
- `duration-bucket` dedupe will falsely merge two different 4-minute
  recipes that share a normalized title. We bucket at 30s granularity
  to limit the collision surface; tune this when real data lands.
- The yield estimator takes upstream `totalHits` at face value; many
  APIs cap listing counts, so numbers above ~10k should be treated as
  censored, not as a true count.
