# Adversarial-Agent Plan — 2026-07-17

Previous plan: `docs/plan-2026-06-20.md`. Previous baseline:
`reports/baseline-2026-06-20.json` — quality ranking
`wikimedia 0.62 > peertube 0.57 > common_crawl 0.53 > archive_org 0.36`.

## Standing hypothesis (unchanged)

> H1. A quality-weighted blend across permissively-licensed open-web
> sources Pareto-dominates any single source on
> `yield × license-cleanliness × resolution × procedural-density` for
> cooking video.

## New sub-hypotheses under attack today

- **H2 (License-classifier confidence).** Every adapter today re-invents a
  regex over license URLs / short-names. Different adapters disagree on
  edge cases (e.g. `by-nc-sa` vs `by-sa`, GFDL, PDM). A single
  well-tested classifier that emits `(License, confidence)` will reduce
  mislabels and let downstream code reject low-confidence records.
- **H3 (Cross-source duplication is meaningful).** Many hobbyist cooks
  cross-post the same video on Wikimedia Commons *and* Internet Archive
  (or two PeerTube instances). Without dedup, our "internet-scale"
  numbers double-count identical content. A cheap normalized-title +
  duration-bucket hash should find ≥1 duplicate on our own fixtures once
  we cross-post fixtures.
- **H4 (Procedural density > `has_steps` boolean).** Counting *imperative
  cooking verbs* in title/description/steps is a strictly stronger
  signal than the current 0/1 `has_steps`, and correlates better with
  intent-driven world-modeling utility.
- **H5 (English-only lexicon undercounts non-English cooking).** A
  multi-lingual (EN/ES/FR/IT/JA/HI) seed lexicon will re-rank corpora
  that contain non-English titles/descriptions. Absent this, we
  systematically under-select global cooking content.
- **H6 (Openverse aggregates enough new signal to change the
  ranking).** Openverse indexes CC-licensed media across Wikimedia,
  Flickr, Europeana, etc. Adding it as an adapter should either (a)
  raise the aggregate license-clean count with no drop in mean quality,
  or (b) be dropped from the roster with a documented reason.

## Adversarial questions to attack

1. **How wrong is our license labeling today?** We assume regex hits.
   Under a held-out set of 10 crafted URLs, what percentage do we get
   right at the (license, confidence≥0.8) threshold? Baseline: not
   measured. Target: publish confusion counts in a report.
2. **What happens if the same record shows up in two sources?** Today,
   nothing — we'd count it twice. Adding cross-source dedup should
   *reduce* `__total__.n_records` by any duplicates and *not* reduce
   `unique_authors`.
3. **Do different weight configurations of the quality scorer produce
   different source rankings?** If yes, we cannot claim any single
   source "wins" without an ablation. Deliver an ablation harness that
   emits per-config ranking on the same fixture set.
4. **Is the roster still Pareto-dominated by cheap additions?** Add
   Openverse and re-measure. Cheap wins should compound.

## Allowlist justification: Openverse

Openverse (openverse.org, WordPress Foundation) is a first-party
aggregator whose entire scope is *only* permissively-licensed media
from sources that already publish under CC / PD terms
(Wikimedia, Flickr CC pool, Europeana, Museums Victoria, etc.). It
exposes a public JSON API. This is consistent with the existing
allowlist and adds coverage of long-tail sources we don't index
directly. Records still carry the *upstream* license URL and provider,
so provenance is preserved.

## Out of scope today

- Actual video frame extraction / download.
- Deep audio/vision quality models.
- YouTube CC listings (still allowlisted but requires an API key we
  won't put on CI today).

## Risks the next reviewer should challenge

- The multilingual lexicon is intentionally tiny (seed only). A
  reviewer should push for a larger, community-curated list *with the
  same offline-testable interface*.
- Dedup by normalized title will over-merge generic titles ("Pasta
  Recipe"). Mitigation: require both title *and* rounded-duration match
  before merging. This may still be too aggressive; ablate on real data
  next cycle.
- Openverse aggregates from many upstreams; if their license mapping is
  wrong, we inherit the bug. We store their claimed `license` alongside
  a `license_url` so we can audit.
