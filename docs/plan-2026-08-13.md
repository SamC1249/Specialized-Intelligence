## What the baseline actually shows

`reports/baseline-2026-06-20.json` (`mean_quality` per source, offline
fixtures, terms=`cooking recipe`):

| Source        | n | mean_quality | notes                                                  |
| ------------- | - | ------------ | ------------------------------------------------------ |
| wikimedia     | 2 | 0.62         | best of the four; small fixture                        |
| peertube      | 2 | 0.57         | licence-ID filter works; language rarely surfaced      |
| common_crawl  | 1 | 0.53         | zero license-clean records — page license unknown      |
| archive_org   | 3 | 0.36         | duration parsing works, but resolution never set       |
| **__total__** | 8 | **0.50**     | new work must beat this on the same fixtures           |

Concrete weaknesses this plan attacks:

1. **`compare --fixtures` is a lie.** The CLI currently returns *empty*
   record lists in fixtures mode, so `reports/ci-compare.json` is a
   zero-record artifact. The offline e2e test path is the *only* real
   check. We must fold fixtures into the CLI so CI publishes a report
   equivalent to the e2e test.
2. **No cross-source dedup.** A Prelinger cooking video mirrored on
   Wikimedia Commons and Internet Archive is counted twice, inflating
   yield and biasing mean_quality against low-duplication sources.
3. **No language signal.** `SourceQuery.language` is defined but never
   consumed. Multilingual cooking footage (es/ja/fr/…) is invisible to
   ranking.
4. **Procedural density is binary.** A 12-step recipe scores the same
   `has_steps` = 1.0 as a 2-step one. Frontier world-model value is
   monotone in procedural depth.
5. **`search()` is untested.** Every unit test hits `parse()` against a
   fixture; nothing exercises URL construction / param encoding /
   error handling of `search()`. A silent regression in query assembly
   would not fail CI.
6. **Weights are asserted, not measured.** Today's weight vector is a
   guess. We have no ablation harness so future weight PRs can't prove
   they beat the baseline.

## Hypotheses under test

- **H2 (language signal).** A metadata-only `detect_language(text)`
  heuristic (unicode-range + stop-word lookup, zero deps) can label ≥ 90%
  of English cooking records correctly on fixtures, and enables
  `SourceQuery.language` to actually filter.
- **H3 (procedural density > has_steps).** Replacing the binary
  `has_steps` component with a continuous `procedural_density`
  (imperative-verb starts across title + description + recipe_steps,
  saturating around 8 steps) *and* re-weighting will improve total
  mean_quality without harming any source individually.
- **H4 (cross-source dedup is real).** A conservative
  `(normalised_title, duration_bucket)` fingerprint reveals overlap
  between our own fixtures (we plant a Wikimedia / Archive pair to
  guarantee CI catches the code path) and this overlap matrix is a
  durable metric worth tracking in every report.
- **H5 (ablation makes weight PRs falsifiable).** Running the same
  fixture universe under N weight vectors reveals whether a change is a
  *systematic* improvement or a single-source artefact.
- **H6 (multilingual seed terms increase yield).** Once the multilingual
  seed lexicon exists, the same adapters will produce *more* records on
  simulated non-English fixtures, and `compare --multilingual` becomes
  the standard mode for future benchmarks.

## Risks the next reviewer should challenge

- Language detection based on character ranges + stop words is coarse
  and will misfire on short titles or transliterated content
  ("sushi" in an English sentence). Mitigation: report a *confidence*
  and use it as a soft filter with `--min-language-confidence`,
  never as a hard drop.
- Dedup on (title, duration) can incorrectly merge two distinct short
  clips (`pancakes.mp4` at 180s). Bucket size and title normalisation
  must be conservative; keep the *union* of provenance URLs on
  collapse.
- Ablation harness must not fork randomness — every weight variant
  must see the exact same input records; else "wins" are noise.
- Rebalancing `WEIGHTS` risks making the new baseline appear better
  simply because the scale changed. Guard with a *ratio* regression
  test, not an absolute one; and commit the report *before* the guard
  adjustment so history is transparent.
