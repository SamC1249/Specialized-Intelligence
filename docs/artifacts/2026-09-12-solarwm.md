# SolarWM: Open Data and Scalable Training for Long-Horizon Video World Models

**Citation.** Junchao et al., 2026. arXiv:2609.02886.
<https://arxiv.org/pdf/2609.02886>. Code & data:
<https://github.com/Junchao-cs/SolarWM>.
Data release: <https://huggingface.co/datasets/junchaoh-cs/SolarWM-Data>.

## One-line summary

Fully-open interactive video world model built on top of 1.43M canonical
clips from 10-14 heterogeneous datasets, unified into a single
"frame-aligned contract" of observations + metric camera geometry +
captions + quality metadata + **selection decisions** + provenance.

## Why this matters for us

The mission (`AGENTS.md`) is "internet-scale, legally accessible" data
for frontier world models. SolarWM is the first fully-open pipeline in
2026 that shows *what* a training-ready record actually looks like. If
we want our `VideoRecord` to be a superset of what a world-model trainer
wants, SolarWM is the reference.

Key structural insights:

- **The unit of ingestion is a *canonical clip*, not a video.** Their
  pipeline splits, resamples, and normalizes before anything else runs.
  Our current `VideoRecord` still corresponds to an entire upstream
  video. We will need a `Clip` sibling type once we ingest anything
  beyond metadata.
- **Selection decisions are first-class data.** They ship
  `selection.jsonl` per source: for every record they *rejected*, the
  reason code stays. This is exactly the missing half of our
  benchmark harness — we log `n_records` but not why records were
  dropped.
- **Camera geometry is metric.** They estimate absolute-scale camera
  trajectories so downstream models can be camera-conditioned. Even
  though we are metadata-only today, our schema should keep a
  `camera_geometry: dict | None` slot so we don't have to migrate later.
- **Source-processing is decoupled from mixture construction.** Each
  adapter is a pure function into the canonical contract; mixtures are
  built afterwards from those artifacts. This is already the shape of
  our `BaseSource` + `compare/` split — we should keep it that way.

## What to steal

1. **Add "rejection with reason" as a first-class output.** Extend the
   comparison harness to return a `RejectionReport`: per-source count
   plus one row per rejected record with `reason ∈ {no_license,
   duration_out_of_bounds, near_duplicate, unknown_media_url, …}`. We
   can start with just `near_duplicate` today (see
   `2026-09-12-video-dedup.md`).
2. **A unified "training-ready contract".** SolarWM's `raw-wds/`
   structure is WebDataset shards keyed by (source, canonical clip id).
   Our `VideoRecord.id` already uses `f"{source}:{native_id}"`; add a
   `clip_id: str | None` field that will hold `f"{video_id}#t{start}s"`
   once we split.
3. **Annotation-only releases.** Their release ships *only*
   annotations, requiring the downloader to fetch original videos from
   the source publishers. This is exactly the pattern we should use for
   any dataset we publish: URL + license + annotation, never bulk
   media redistribution.
4. **Documented dataset provenance table.** They list every source
   dataset with its license, sample count, and "reason for inclusion".
   We should build the same table under `docs/sources.md` before the
   next source PR lands.

## What to not steal

- Their `Wan2.2 / LTX-2.5 / MiniMax-H3` backbone-specific adaptation
  layers — that's a training-side concern, orthogonal to our data
  charter.
- Their choice to include some datasets that ship under
  research-only licenses (e.g. EPIC-KITCHENS CC-BY-NC-4.0) is not
  compatible with our redistributability tier; we can *link* to those
  datasets from our provenance table but we cannot mirror any of
  their annotations.
