## The baseline is fragile — three attacks worth running

### A1. Cross-source duplication inflates yield.

Wikimedia Commons routinely mirrors Internet Archive uploads (and
vice-versa). PeerTube instances federate: the *same* Framatube video is
also served from `tilvids.com`. Every duplicated record in a source's
listing is an extra false hour we'd double-count during a download
budget decision. **We currently have zero dedup.**

- **Hypothesis H1.** For a query like `["cooking","recipe"]` returning
  N records across all sources, ≥5% will be near-duplicates by
  (normalized title, duration bucket) match, and ≥1% will be exact
  URL matches after canonicalization (strip UTM, lowercase host, drop
  trailing slash).
- **Test.** Add a fixture that intentionally seeds a duplicate across
  `wikimedia` and `archive_org`; assert the dedup pass collapses them
  to a single record and preserves the *strongest-license* copy.

### A2. Quality score ignores procedural density.

Recent world-model benchmarks (WorldPrediction, ArXiv 2506.04363;
WBench, ArXiv 2605.25874) show that frontier models fail at
**semantic-abstraction-level** procedural planning — not perceptual
fidelity. Our current `quality/metrics.py` mostly rewards resolution and
duration. It doesn't reward *procedural information* — the very signal
world models need most.

- **Hypothesis H2.** Adding a `procedural_density` metadata component
  (# recipe_steps, verb-like tokens in title/description, presence of
  time/temperature tokens) reranks `wikimedia` above `common_crawl` on
  the same fixtures, matching a hand-labelled judgement.
- **Test.** New unit test: a hand-crafted `VideoRecord` with 10 steps
  and 5 imperative verbs beats an equal-duration, equal-resolution
  record with an empty description.
- **Comparison rule.** The metric must ship with a re-run of the
  benchmark harness and a fresh `reports/compare-2026-07-18.json`;
  the plan.md line must state whether it moves the source ranking.

### A3. Search-term-only discovery under-samples Commons.

Free-text `gsrsearch=cooking filetype:video` misses videos whose page
lives in `Category:Videos of cooking` (75 files as of 2026-07)
without matching either token in title or description. The MediaWiki
`categorymembers` generator is a strictly higher-recall path when the
category exists.

- **Hypothesis H3.** For queries mapping to a known Commons category
  (a small hand-maintained map is fine for now), categorymembers
  discovery increases license-clean record count by ≥30% at the same
  `max_results` cap, without lowering mean quality.
- **Test.** New fixture `wikimedia/category_cooking.json` shaped like
  the real API response; assert the parser handles both `search` and
  `categorymembers` payloads through the same `parse(raw)` entry
  point.

## Adversarial questions carried into next plan

1. **Multilingual seed terms.** English-only "cooking" misses the entire
   corpus of `cuisine`, `recette`, `料理`, `receta`, `küche` videos.
   Do we ship a language-aware `SourceQuery` next?
2. **JSON-LD trust.** Common Crawl `contentUrl` fields are unreliable
   (recipe sites embed hotlinked YouTube). Should we drop
   `contentUrl` records whose host ≠ page host?
3. **Frame-level provenance without media download.** Can we compute a
   perceptual fingerprint from thumbnail images alone (Commons exposes
   them) so dedup catches re-encodes, not just re-titled uploads?
4. **PeerTube instance diversity vs. license drift.** Federated hosts
   sometimes re-federate videos whose upstream license changed.
   Snapshot licenses at fetch time, never trust downstream.

## Out of scope today (still)
