## Hypotheses under attack today

> **H2 (Yield-floor).** The current 4-source registry under-counts
> internet-permissive cooking footage by at least an order of magnitude.
> Two missing high-signal sources (Vimeo CC via the public API's
> `filter=CC` and Flickr via `flickr.photos.search` with
> `license=4,5,7,8,9,10` + `media=videos`) can **each** add ≥ 1 record
> to the fixture baseline and, when run live, project to ≥ 10× more
> license-clean candidate videos per crawl-day than the current
> registry. Openverse was initially considered but currently has no
> video endpoint; it is deferred.
>
> **H3 (Dedup-ceiling).** With no cross-source deduplication, the harness
> double-counts the same upload mirrored across Wikimedia, Internet
> Archive, and PeerTube. A metadata-only dedup (normalised title + ±5%
> duration + author) will remove 10–30% of the raw yield once the corpus
> grows past ~10³ records, and this reduction *is* the quality signal.
>
> **H4 (License-safety invariant).** The system **currently has no
> automated proof** that we never emit a `media_url` for a non-
> redistributable record. The baseline passed by inspection, not by test.
> A property-style invariant test over every fixture will either confirm
> safety or expose a bug — this is more important than any new source.
>
> **H5 (Schema drift).** `db_structured.md` is declared the single source
> of truth, but nothing in CI fails when a Pydantic field drifts away
> from the markdown table. A contract test that parses the markdown and
> diffs against `VideoRecord.model_fields` is the cheapest guard rail
> we're missing.

## Attacks on the existing design (specific, actionable)

1. **Wikimedia search is a weak harvester.** Commons' `Category:Videos
   of cooking` has only ~74 files total; our `gsrsearch=cooking` call
   misses most of them because Commons' search ranks over textual match,
   not categorisation. **Follow-up:** add a `generator=categorymembers`
   path to the Wikimedia adapter and walk `Category:Videos_of_cooking`,
   `Category:Videos_of_cooking_recipes`, and
   `Category:Videos_of_cooking_from_India` recursively (bounded depth).
   Yield prediction before implementation: ~400–800 clips cross-language.
   *(Flagged for next plan; today's PR adds the yield-projection utility
   that will let us measure the gain.)*

2. **PeerTube license filter trusts the ID.** Our adapter treats
   PeerTube's `licence.id ∈ {1,2,7}` as ground truth. In practice,
   uploaders mislabel; we should also demand that the instance itself
   publishes a redistribution-friendly ToS. **Follow-up:** add a tiny
   per-instance `instance_license_ok: bool` allowlist, defaulting to
   `False` for any instance we haven't vetted. Today: document the gap
   in the Vimeo adapter so it does not repeat the mistake (Vimeo's
   `filter=CC` is likewise a *hint* — we re-verify from the per-item
   `license` field).

3. **Common Crawl adapter is a stub.** `search()` returns `[]`. Without
   WARC iteration we can't actually produce yield. The right production
   path is to query the Columnar URL Index (Parquet on S3), filter to
   HTML pages with `content_mime_detected = 'text/html'` and
   `content_languages` matching our target, then fetch WARC byte-ranges
   for the hits. **Follow-up:** write a `common_crawl_index.py`
   DuckDB-over-Parquet query helper with a *tiny* local parquet fixture
   so tests remain offline. Noted for the next plan.

4. **Quality scoring is single-shot.** Current weights
   (license 0.35, duration 0.15, resolution 0.20, text-density 0.15,
   has_steps 0.15) are declared, not justified. Panda-70M, Sekai and
   Cosmos' cookbook *all* use multi-stage filters: shot-boundary, motion,
   luminance, OCR/watermark, VLM semantic validation, dedup. We cannot
   do pixel work in CI, but **dedup is table stakes and runnable from
   metadata alone**. That is today's quality upgrade.

5. **No contamination guard.** We may re-ingest a video that already
   appears in a public eval set (YouCook2 IDs, Ego-Exo4D takes).
   Follow-up: ship a `contamination.py` that reads a checked-in list of
   known-held-out YouTube IDs / Commons titles and blocks them from
   `media_url` emission.

6. **Pre-commit lies about mypy.** CI runs `mypy src || true`. That is
   not a type check; it's decoration. Promote `records.py` and
   `compare/harness.py` to `strict = True` because they are the public
   contract.

7. **No live-API integration canary.** Fixtures rot. The upstream
   schemas (MediaWiki `extmetadata`, PeerTube API, Vimeo video response)
   do change. Follow-up (next plan): add a nightly workflow that runs
   `SPECINT_RUN_INTEGRATION=1 python -m specint compare --only wikimedia
   --max-results 3` against the real APIs and alerts on parse errors.

## Risks the next reviewer should attack

- **Vimeo API ToS.** Vimeo's `filter=CC` returns hints; the authoritative
  field is per-item `license`. We default-reject anything not in {`by`,
  `by-sa`, `cc0`}. If Vimeo later changes the response shape, our
  schema-contract test will *not* catch it — only a live integration
  test will. Document this loudly in `vimeo.py`.
- **Openverse coverage.** When Openverse exposes a `/v1/videos/`
  endpoint (planned upstream), landing it will double-count Wikimedia
  and Flickr videos unless dedup runs across pooled results. The
  `quality/dedup.py` shipped today is the mitigation.
- **Flickr media URL.** Flickr's public API does not expose a direct
  video stream URL for every account; our adapter prefers `url_o`
  through `url_m` fallbacks and the Flickr landing page is always
  present on `url`. Live `search()` will need to be validated against
  response shape drift once we onboard an API key.
- **Dedup key is coarse.** `round(duration, -1)` buckets to the nearest
  10 s, which can collide for ad-break-length clips. The intent is to
  trade a few false-positive merges for strong recall; the chosen merge
  policy prefers the stricter license so an incorrect merge *reduces*
  training yield rather than contaminating it.
- **Bandit will flag our `httpx.Client(...)` with `verify=True`
  defaults** — that's fine; we accept the signal. Any new network call
  must justify itself.
