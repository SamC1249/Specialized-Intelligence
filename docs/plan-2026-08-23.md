## Hypotheses under test

> **H2. Multilingual seed terms materially expand yield without hurting
> mean quality.** English-only "cooking / recipe" queries under-sample
> Wikimedia Commons and PeerTube — global cooking traditions are indexed
> under their native names ("料理", "receta", "recette", "Kochen", ...).
> Adding a curated multilingual seed list should increase raw record
> count on the same fixtures/live searches without degrading
> `mean_quality`.

> **H3. Naive per-source aggregates over-count the corpus.** Wikimedia
> re-uploads (mirrored PeerTube uploads, Internet Archive re-hosts of
> Commons files, etc.) inflate `n_records` across sources. A cheap
> metadata-only dedup (normalized title × rounded duration) should shrink
> the aggregate `__total__` by a measurable percentage even on the tiny
> baseline fixtures.

> **H4. "Cooking-ness" is a stronger quality signal than raw
> text_density.** A record's title/description can be long yet
> irrelevant. A multilingual **cooking vocabulary hit-rate** score
> should Pareto-dominate the current `text_density` component:
> baseline mean_quality on cooking-tagged fixtures should go up, and
> mean_quality on a non-cooking control fixture should go down.

> **H5. YouTube's `videoLicense=creativeCommon` slice is legally clean
> enough for URL+metadata harvesting.** We do **not** download media.
> The adapter only lists CC-BY videos and records their (URL, title,
> license) triples for future licensed transcript / caption use.

## Why these are frontier problems

- Cooking video is a canonical long-horizon, procedural, partially-
  observable domain (irreversible state changes: emulsify, caramelize,
  denature). Multilingual coverage is *the* difference between "a
  Western-cooking model" and "a world-cooking model".
- Deduplication is a hard, unsexy backbone problem for any
  internet-scale crawl. If we do not solve it in the metadata layer we
  will pay 10× for it in storage and training-compute later.
- License signal quality is our single biggest legal risk vector; the
  more diverse our sources, the more we need principled, auditable
  license classification.

## Adversarial questions to attack today

1. **Does adding non-English seeds actually surface new records** or do
   the existing English fixtures already dominate? If not, we need to
   document *why the experiment was still informative* (per AGENTS.md
   Comparison-First Rule).
2. **Is our dedup fingerprint collision-safe** for common cases like
   the same recipe uploaded at different resolutions? Design it so
   colliding records are merged into the highest-quality-clean
   representative.
3. **Can `youtube_cc` be exercised entirely offline** — no live API key
   at unit-test time — while still emitting a real license-clean
   `VideoRecord`? (Yes: put the adapter behind fixtures and hide the
   live path behind `YOUTUBE_API_KEY`.)
4. **Do we regress the current baseline** (`reports/baseline-2026-06-20.json`)?
   The new baseline **must** be committed to `reports/` with a diff
   note in `plan.md`.

## Out of scope today

- Live YouTube API calls in CI (requires user-provided API key).
- Cross-language *content*-based dedup (title translation, perceptual
  hashing on frames). Metadata-only fingerprint is a deliberately
  conservative first cut.
- WARC-scale Common Crawl iteration (still fixture-driven).

## Risks the next reviewer should challenge

- Vocab lists are hand-picked and small; they will bias against
  cuisines whose vocabulary we forgot. Mitigation: keep vocab data in a
  single reviewable module and treat it as a config.
- Dedup by rounded duration will collapse legitimately distinct short
  recipes (e.g. two different 60s pancake videos). Mitigation: keep
  the delta observable in `BenchmarkResult` so a reviewer can see how
  aggressive dedup is being.
- YouTube's ToS is subtle: we harvest **metadata only**, never media,
  and every record must carry `license=CC_BY` + `url` pointing back to
  the YouTube watch page. The adapter must refuse to emit `media_url`.
